# Token efficiency and record growth

Working notes for the `token-efficiency` branch. Written 2026-08-22. This is an
engineering record, not user documentation: it exists so the measurements and the
reasoning behind v1.4.0 survive the session that produced them, and so the parts
that are still open can be picked up without re-deriving anything.

Everything below was measured read-only against a real forge-managed project,
`autotask-focus-bridge`, which was under active development at the time. Nothing
in that repository was modified.

---

## 1. What was measured

The project had been running the forge lifecycle for twenty days
(2026-08-02 to 2026-08-22).

| Artifact | Size | Shape |
|---|---|---|
| `CONTINUE.md` | 118,767 B / ~30,153 tok | 1,383 lines. 33.7 percent retrospective: seven `What T-XXX shipped` sections, `The rest of the backlog, unchanged`, `What just happened` |
| `TODO.md` | 639,206 B / ~160k tok | Completed 472,316 B (73.9 percent). Backlog 58.7 percent closed-task narrative: 16 CLOSED entries against 6 genuinely open |
| `docs/DECISIONS.md` | 1,031,625 B / ~258k tok | 215 dated entries, 20 days, ~50 KB/day, average 4,888 B/entry |
| `docs/traceability.md` | 304,738 B | 317 rows, 6 columns, hand-maintained, average 873 B/row |
| `docs/SRS.md` | 166,689 B | Section 34 Change Log is 51,577 B, 30.9 percent of the requirements document |

Per-session context floor before any work: `forge` + `forge-standards` skills
34,106 B, project `CLAUDE.md` 24,678 B, `CONTINUE.md` injected whole 118,767 B.
About 43,000 tokens, of which roughly 9,500 was duplicate history.

Literal compliance with the read-first lists was impossible. `forge-code` named
seven documents totalling 2,311,849 B, about 578,000 tokens. `forge` Step 1 named
six totalling about 322,000 tokens. Both exceed any context window, so the
instruction was already being executed partially and silently, which matters
because the reconcile-before-acting gate was running on an undeclared partial
read.

## 2. The failure modes, with evidence

**Layered corrections coexisting in the injected file.** `CONTINUE.md:17` stated
"section 30's thirteen criteria ... Six of the thirteen are already met" while
`:30` stated "The bar is fourteen criteria now, not thirteen, and eleven are met".
A top-down reader meets the stale claim first. The file also carries, at `:24`,
"Two things this file used to claim that are false, corrected here so they do not
propagate", which is the same failure recorded by hand.

**Write amplification.** One closed defect, UXD-031, was narrated 17 times across
three files. FR-ATS-004 was restated in five files with five independent prose
renderings. The derivative sentence "excluded from the coverage floor by
established precedent" appeared verbatim 6 times in `TODO.md` and 5 times in
`docs/DECISIONS.md`. The rules require a slice closure to be written to four or
five artifacts with no owner assigned per fact, which is how the artifacts come to
disagree.

**Hand-maintained tables rot where nothing checks them.** Eight rows of
`docs/traceability.md` have narrative prose in the Status column: FR-APP-001,
FR-APP-005, FR-APP-007, FR-APP-008, REL-010, PERF-005, FR-ATS-011, UX-001. The
same file had its column boundaries destroyed once before and was rebuilt cell by
cell. A schema check would have caught both.

**No ceiling existed anywhere.** A grep of the whole ruleset for
archive/prune/compact/trim/rotate/truncate/retain/ceiling/rollover found exactly
one archival rule: a comment in `templates/TODO.md` reading "Archive to
docs/DONE-ARCHIVE.md when this passes ~50 entries". No skill referenced it, so the
Completed section reached 155 entries, three times the never-enforced threshold.

## 3. Not a problem

`.gitignore` correctly excludes `TestResults/` (352.6 MB, 794 `.trx` files, about
50 test runs per day), `coverage/` (19.6 MB), and `.codegraph/` (35 MB), so none of
it reaches git or CI. It is disk cost and a trap for anything that globs the tree,
nothing more. `CHANGELOG.md` is generated by git-cliff. `scripts/stop-check.js`
reads no file contents and already caps its own output.

## 4. Shipped in v1.4.0 (Stage 0)

Caps and ownership, no new infrastructure, reversible.

- `scripts/session-start.js` selects rather than truncates. Budget 20,000 chars,
  set so a file honouring the 200-line ceiling is never capped. Always injects the
  ladder fields with wrapped values kept whole, then the sections describing what
  happens next in priority order. Nothing else is injected however much budget
  remains. Withheld sections are named with their sizes. A record whose sections
  are named something else falls back to its opening rather than to state fields
  alone.
- `forge-standards` gained a Record hygiene section: 200-line ceiling on
  `CONTINUE.md`, one fact one owner, correct by superseding rather than layering,
  Completed archives past 50 entries, a CLOSED task leaves the backlog in the edit
  that closes it.
- `forge-code` and `forge` Step 1 read lists are scoped by section and by ID, and
  both state that a partial read is fine while presenting one as complete is not.
- `templates/CONTINUE.md` and `templates/TODO.md` carry the ceiling and the
  archive threshold where a project actually reads them.
- `tests/record-budget.test.js`, 11 tests, including two that a positional cut
  cannot pass by construction.

Measured on the real 118 KB file: 30,153 tokens down to 3,255, with the next
action and the open blocker both present and zero retrospective sections injected.

Two bugs the smoke test caught, both now pinned: a wrapped `Capabilities:` value
was clipped mid-sentence, and `Blocked on me` lost the budget race to the long
narrative section. Also corrected: the first cut of this work set a 12,000-char
budget against a 300-line ceiling, meaning a compliant file would still have been
capped. A test now fails if the two numbers ever disagree again.

## 5. Prompt caching: why it does not moot any of this

Verified against the Anthropic docs: cache write is 1.25x base input (5-minute
TTL) or 2.0x (1-hour), cache read is 0.1x, matching is prefix exact, any byte
change before the breakpoint is a miss, the 5-minute TTL refreshes free on each
read, and the minimum cacheable prefix is about 1,024 tokens.

Caching is a per-token multiplier, so it scales a large injection and a small one
by the same factor and cannot change the ratio between them. For a 40-request
session the injection alone costs about 155,288 token-equivalents before this work
and about 16,764 after: 9.3x either way.

What caching does not touch:

- **Window occupancy.** 30,000 cached tokens occupy 30,000 tokens of the window.
  Fifteen percent of a 200k window is gone before the first line of code is read.
- **Attention.** The thirteen-versus-fourteen contradiction is a correctness
  defect. Caching preserves it at a 90 percent discount.
- **The 578,000-token read list.** That was never a cost problem. It does not fit,
  and each of those reads is fresh input mid-conversation, so a write rather than
  a read.

Where caching makes growth worse rather than better:

- **Invalidation tracks churn.** `forge-standards` requires `CONTINUE.md` be
  rewritten whenever the next action changes, which is every slice, so a large
  injection is re-written at the write premium as often as it changes.
- **Human pacing loses the TTL.** Five minutes, refreshed only on a read. A gap
  while the user reads something means the next request pays a fresh 1.25x write.
  Intermittent use is the common case and the one a fat prefix punishes.

Two corrections to earlier framing in this work, recorded so they are not
repeated: the "43k per session" figure is window cost, not billed cost (billed
recurring is about 0.1x of it once cached), and the first request of every session
is *more* expensive than uncached, not less, because a write is 1.25x.

**A trade taken deliberately.** Prefix caching preserves everything before a
change, so appending is cache-friendly and correcting in place is cache-hostile.
The Record hygiene rule "correct by superseding, not by layering" is therefore the
more expensive option on billing grounds. It stays: a discount on reading the
wrong number is not a saving. Stage 1 dissolves the tension, because correcting
one small record invalidates that record rather than a 1 MB monolith.

**Unverified.** Where Claude Code places its cache breakpoints, and whether
SessionStart hook output falls inside a cached prefix, is not documented. The
reasoning above does not depend on it, because the window-occupancy argument is
independent of caching. It is measurable rather than researchable: see the test
plan below.

## 6. Stage 1, designed and not built

Records as files, views generated, graph derived rather than authoritative. The
precedent is `.codegraph/`: 35 MB, gitignored, rebuildable, authoritative about
nothing.

Rejected: a SQLite or graph store as the system of record. SRS approval is a human
gate so the record must be reviewable in a PR; records must diff and merge in git
and two agents already edit that repo concurrently; forge installs as prompt text
plus node scripts. Also rejected: vector or semantic retrieval. Every fact already
has a canonical key, so deterministic ID lookup dominates similarity search, and a
stale embedding on a gated lifecycle is a correctness hazard.

```
docs/records/{decisions,requirements,tasks,uxd}/<id>.md   authoritative, small
docs/views/{traceability,DONE-ARCHIVE,open-work}.md       GENERATED, never hand-edited
.forge/index.json                                          GENERATED, gitignored
CONTINUE.md                                                pointer file, IDs not prose
```

Front matter carries the edges: `id`, `status`, `closes`, `satisfies`,
`supersedes`, `decided_in`. The node and edge vocabulary already exists in the
project as `T-nnn`, `FR-xxx-nnn`, `UX-nnn`, `UXD-nnn`, `OBS-nnn`, `REL-nnn`,
`USA-nnn`, `PERF-nnn`, and the relations closes/satisfies/supersedes/covered-by.
The graph is present and unindexed; what is missing is that each node has no
address.

What it buys, in order of importance:

1. **Write once instead of five times.** A slice close edits one task record and
   appends one decision record; the views regenerate. This is the maintenance
   burden, and retrieval cleverness does not fix it.
2. **Supersession becomes resolvable.** History is preserved and the generated
   working set shows only live records, so a file cannot assert two answers.
3. **Deterministic retrieval.** One 2 KB record read instead of a grep across
   1 MB.

**Feasibility, measured rather than assumed.** A live-state index built from the
real records (phase, gate, mode, 6 open tasks, 12 open UXD rows, 91 gap
requirements) came to **3,017 B / ~754 tokens**, against `CONTINUE.md` at
118,767 B: 39x. Edge inference from the existing prose is mechanical: of 215
decision entries, **92 percent already name a `T-id`, 72 percent name a
requirement ID, 6 percent are orphans**, median 7 IDs per entry. Migration is a
one-time script plus human review of the orphans.

**The trap.** An index enumerating all 317 requirements plus 138 tasks plus 61
UXD rows is about 42 KB, which recreates the problem one level up. The index
carries live state only; history stays addressable and is never enumerated.

**Non-negotiable guard.** A PostToolUse hook must refuse hand-edits to
`docs/views/**`. A generated file that anyone may edit becomes an unreliable
hand-maintained file within a week, which is exactly how `traceability.md` became
305 KB of prose with eight broken Status cells.

**Needs three real programs** in `templates/`: indexer, view generator, and a
records linter (IDs unique, every edge resolves, no dangling supersede, no
orphan). Precedent exists: `branch-protection.js` and `history-guard.js` are real
tested programs shipped in `templates/`.

**Ship it as a versioned capability with a backfill offer**, using the mechanism
`CLAUDE.md` already describes: an older project is not a broken project, the
answer lands in the `Capabilities:` line, a recorded skip is honoured. Migration
of an existing 2.3 MB record set is its own slice, taken with the working agent's
consent, never mid-slice.

Stage 2, an actual query layer, only if a question appears that IDs and grep
cannot answer. Currently no evidence one exists.
